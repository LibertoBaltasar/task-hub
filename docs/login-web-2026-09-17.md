# Login web real: Google Sign-In (GIS) en wasmJs — 2026-09-17

## 1. Cómo se implementó

Contrato existente sin tocar: `GoogleAuthManager.signIn()` → `launchGoogleSignIn()`
(expect) → `GoogleSignInResultHolder.setResult(idToken | "")`. Solo se ha
implementado el `actual` de wasmJs, que antes era un no-op inmediato.

### Archivos tocados

- `composeApp/src/wasmJsMain/resources/index.html` — fuente EDITABLE del
  `index.html` de salida (se copia tal cual a `build/dist/wasmJs/.../index.html`
  vía `wasmJsProcessResources`/`wasmJsBrowserDistribution`; no es generado
  desde una plantilla de plugin). Se añadió:
  1. `<script src="https://accounts.google.com/gsi/client" async defer></script>`
     en el `<head>`.
  2. Un `<script>` inline con el puente JS↔Kotlin (`window.__taskhubGis`,
     `__taskhubStartGoogleSignIn`, callbacks de `initialize`/`prompt`).
- `composeApp/src/wasmJsMain/kotlin/org/taskhub/platform/Platform.wasmJs.kt` —
  `launchGoogleSignIn()` real: arranca el puente JS y sondea el resultado por
  polling (ver mecanismo de interop abajo).
- `composeApp/src/commonMain/kotlin/org/taskhub/platform/GoogleOAuthConfig.kt`
  (nuevo) — constante `GOOGLE_WEB_CLIENT_ID` compartida entre Android y web.
- `composeApp/src/androidMain/kotlin/org/taskhub/GoogleSignInHelper.kt` —
  cambio trivial: `WEB_CLIENT_ID` ahora referencia `GOOGLE_WEB_CLIENT_ID` en
  vez de duplicar el literal (sin cambio de comportamiento).

### Mecanismo de interop wasmJs elegido, y por qué

**Intentado primero (según el encargo): pasar un callback de Kotlin
directamente a `google.accounts.id.initialize({ callback: ... })`.** Se
descartó sin necesidad de forzar un fallo de compilación: Kotlin/Wasm no
tiene en este proyecto ningún precedente de convertir un lambda Kotlin en una
función JS invocable desde fuera (los únicos usos de `@JsFun` existentes
—`jsSecureRandomInt`— solo intercambian tipos primitivos/String como
argumentos y valores de retorno, nunca funciones). Apostar por esa vía
introducía riesgo real de bloqueo a mitad de tarea sin alternativa clara si
no compilaba o se comportaba de forma inesperada.

**Solución adoptada: el puente vive enteramente en JS (definido en
`index.html`), y Kotlin solo intercambia primitivos/`String` con él vía
`@JsFun`, que es el patrón ya probado en el proyecto:**

- `window.__taskhubGis = { state, value }` — estado compartido en JS.
- `__taskhubStartGoogleSignIn(clientId)` (JS, en `index.html`) — hace polling
  a `window.google.accounts.id` (por si el script `async defer` de GIS no ha
  cargado aún), llama a `initialize({ client_id, callback, auto_select:
  false })` y a `prompt(notificationCallback)`.
- El `callback` de `initialize` (solo se dispara si el login tiene éxito)
  escribe `{ state: "done", value: credential }`.
- El callback de `prompt` (se dispara también ante `isNotDisplayed`/
  `isSkippedMoment`/`isDismissedMoment`, es decir, cancelación o prompt
  bloqueado) escribe `{ state: "done", value: "" }` si aún no se había
  resuelto — así una cancelación no deja el estado colgado en `"pending"`.
- Del lado Kotlin (`Platform.wasmJs.kt`), tres `external fun` con `@JsFun`
  (solo `String`/`Boolean`, sin funciones como parámetro):
  `jsStartGoogleSignIn(clientId: String)`, `jsGoogleSignInDone(): Boolean`,
  `jsGoogleSignInValue(): String`.
- `launchGoogleSignIn()` lanza una corrutina (`Dispatchers.Default`, scope
  propio del archivo) que sondea `jsGoogleSignInDone()` cada 200 ms hasta que
  resuelve o hasta un timeout de seguridad de 120 s (por si GIS ni completa
  ni notifica cancelación — p. ej. un bloqueador de cookies de terceros que
  silencia el prompt). Al resolver, publica el resultado en
  `GoogleSignInResultHolder` con el mismo contrato que Android (idToken en
  éxito, `""` en cancelación/fallo/timeout).

Este mecanismo SÍ compiló a la primera (ver §3) — no hizo falta activar el
plan de contingencia (flujo redirect con `response_type=id_token`).

## 2. Dónde vive ahora el WEB_CLIENT_ID en web

`composeApp/src/commonMain/kotlin/org/taskhub/platform/GoogleOAuthConfig.kt`,
constante `GOOGLE_WEB_CLIENT_ID` (mismo paquete `org.taskhub.platform` que
`Platform.wasmJs.kt`, así que se usa sin import cualificado). Android
(`GoogleSignInHelper.WEB_CLIENT_ID`) referencia la misma constante en vez de
duplicar el literal — un único valor de origen para las dos plataformas.

## 4. Pasos de prueba manual (no automatizable de forma fiable)

1. `cd composeApp/build/dist/wasmJs/productionExecutable && python3 -m http.server 8000`.
2. Abrir `http://localhost:8000` en un navegador — GIS solo admite orígenes
   autorizados explícitamente (ver §5), así que ese origin debe estar dado de
   alta en Google Cloud Console para el Client ID.
3. La app debería mostrar la pantalla de login de Task Hub (gate por UID
   vacío en `SettingsStore`, sin tocar) y disparar el prompt nativo de GIS
   (modal "Elegir una cuenta" / One Tap) al pulsar el botón de Google — o
   incluso de forma automática si el navegador ya tiene sesión de Google (GIS
   puede mostrar el prompt sin interacción previa, ya que `signIn()` llama a
   `launchGoogleSignIn()` inmediatamente).
4. Al elegir una cuenta: el JWT (`credential`) debería intercambiarse por
   credenciales de Firebase vía `signInWithIdp` (`FirestoreRepository`, sin
   tocar) y la app debería navegar a `HomeScreen` con el email de la cuenta.
5. Al cerrar el modal sin elegir cuenta (tecla Esc o clic fuera): la app debe
   volver a `SignedOut` sin quedarse colgada en "Conectando con Google..."
   (contrato de `token.isEmpty()` en `GoogleAuthManager`).
6. Casos límite a observar en la consola del navegador:
   - Si `window.google` nunca aparece (script GIS bloqueado por un
     ad-blocker/CSP): el polling de `tryInit` en `index.html` reintenta cada
     100 ms indefinidamente — el timeout de 120 s del lado Kotlin es el que
     finalmente resuelve a `""`.
   - Si el navegador bloquea cookies de terceros: GIS puede degradar a un
     botón renderizado en vez de al prompt modal; con la implementación
     actual (solo `prompt()`, sin `renderButton()`) ese caso probablemente
     dispara `isNotDisplayed()` y resuelve a cancelación — ver limitación §5.

## 5. Huecos / limitaciones restantes

- **Orígenes autorizados en Google Cloud Console**: el Client ID
  `278503294422-...` (OAuth 2.0 Client ID de tipo Web, del proyecto Firebase
  `task-hub-62f98`) necesita tener registrado el origen exacto desde el que
  se sirva la web (`http://localhost:8000` para pruebas locales, y el
  dominio real de producción cuando exista) en **Google Cloud Console → APIs
  & Services → Credentials → [ese Client ID] → Authorized JavaScript
  origins**. Sin esto, GIS rechaza la inicialización con un error de origen
  no autorizado — no se pudo verificar en este entorno (headless, sin acceso
  a Cloud Console ni a un origen público).
- **Sin fallback a `renderButton()`**: la implementación usa solo
  `prompt()` (el modal/One Tap nativo). Si un navegador concreto suprime
  silenciosamente el prompt (Safari con ITP, o cookies de terceros
  bloqueadas) sin disparar ninguna de las razones de `isNotDisplayed()`
  cubiertas, el usuario solo vería el timeout de 120 s antes de volver a
  `SignedOut` — no hay un botón visible como alternativa. Si en pruebas
  reales esto resulta frecuente, la mejora natural es añadir
  `google.accounts.id.renderButton(...)` en un contenedor DOM como
  fallback visible tras N segundos sin respuesta.
- **No se ha podido probar el flujo interactivo real** (requiere un origen
  autorizado en Cloud Console y un navegador con sesión de Google) — ver
  pasos de prueba manual en §4.
- Calendar (`getGoogleCalendarAccessToken`) sigue sin soporte en web: GIS
  cubre login (idToken), no scopes OAuth adicionales como
  `calendar` — fuera del alcance de este encargo.
